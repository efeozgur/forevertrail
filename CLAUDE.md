# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ForeverTrail is a WoW addon (Lua, Interface 16001, client 1.60.1 "World of Warcraft: Forever") — a quest guide with tracker, map/arrow routing, journal, gear/profession helpers, etc. This repo is linked into the game via a junction (`AddOnsForeverTrail` -> this folder; the old install is kept as `ForeverTrail.bak`), so edits take effect on `/reload` (new files need a full game restart). All user-facing text and the README are in Turkish; keep new UI strings Turkish. There is no build step. Development happens on the `v0.2-dev` branch.

## Commands

- Run a test (plain Lua 5.1+, from the addon root, no WoW client needed): `lua tests/engine.lua` (likewise `tests/map.lua`, `tests/owndb.lua`, etc. — one file per module, each prints/asserts on its own). There is no aggregate runner or linter; run the relevant `tests/*.lua` for the module you changed.
- Tests load modules via `assert(loadfile('Engine.lua'))('ForeverTrail', ns)` with stubbed WoW globals (`C_QuestLog`, etc.), so modules must be loadable with a bare `ns` table. `tests/ingame_sim.lua` simulates a wider client.
- In-game: `/ftrail debug` (client build info + state), `/ftrail test` (self-test), `/ftrail hata` (captured errors), `/ftrail yardim` (command list). Real-client behavior is largely unverified (see README "Doğrulama").

## Folder layout

Lua files live in folders; `ForeverTrail.toc` lists each by path (load order is unchanged). `Media/` and `Bindings.xml` stay at the root, and `tests/` loads modules by the same paths (e.g. `loadfile('Core/Engine.lua')`).

- `Core/`: Core, Compat, Diagnostics, Engine, Quest, Style, Kit (shared flat UI components: tiered fills from the theme, rail button, divider), Design, Polish, Layout
- `Data/`: generated `Data*.lua` tables, `OwnDB`, `OwnData`, `LiveSync`
- `Guide/`: Guides, Guide2, Journal, Recommendations, Recorder, Flow, Journey
- `Map/`: Map, MapRoute, Minimap, MinimapTips, Atlas, Discovery, Objectives, Places, Rares
- `UI/`: Panel, Hub, Tracker, Available, ViewOptions, Target, Arrow, Settings, Features, Toolbox, Extras, Wizard, QuestInfo
- `Helpers/`: Assist, Advisor, Focus, Helpers, Gear, Upgrade, Class, Professions, QuestHelper, QuestItems, Janti
- `Integration/`: Questie*/Queston* bridges

## Architecture

- **No modules/requires.** `ForeverTrail.toc` is the load order and the only wiring: every file starts with `local _, FT = ...` and shares the single addon namespace table `FT`. Adding a file means adding it to the TOC, in a position after anything it uses at load time. Functions are mostly looked up lazily at call time and guarded (`if FT.Foo then ...`), which is how optional modules and the bridges stay decoupled.
- **Entry/events:** `Core/Core.lua` owns the event frame (`QUEST_LOG_UPDATE`, `QUEST_ACCEPTED`, `QUEST_TURNED_IN`, zone changes), debounces to `FT.Evaluate()`, and holds the `/ftrail` slash dispatcher (add new subcommands there, Turkish keywords).
- **Guide engine:** `Guides.lua`/`Guide2.lua`/`OwnData.lua` register guides via `FT.RegisterGuide`; `Engine.lua` validates them (`FT.ValidateGuide`) and decides step completion (`FT.IsStepDone`) from `FT.QuestState` (`Quest.lua`). Step types: `accept|objective|turnin|location|manual`; `stepId`s must be stable across versions because progress is saved by id. Coordinates are normalized 0–1 with `uiMapID`. Guide format is documented in README.md.
- **Auto zone guides (`Guide/AutoGuide.lua`, `UI/GuidePicker.lua`):** `FT.AutoGuide.Build(map, lo, hi)` simulates a leveling walk over the embedded quest DB (race/class/level eligibility, hub-first accepts, chain follow-ups, prerequisites, exclusivity, 16-quest log cap) and returns a normal guide (`auto=true`, ids `a/o/t<questId>`); `Zones()` lists windows, `Select`/`Restore` persist the choice in `ForeverTrailCharacter.autoGuide` (Restore runs in Engine.Initialize before guide choice). The picker window replaces the old Panel list; `/ftrail bolge` opens it. `UI/GuideTab.lua` adds the first tab ("Rehber") to the quest dock (`FT.guideBox`, `FT.RefreshGuideTab`): guide progress, current step card, prev/next, upcoming-step list (row count follows the dock height); it wraps `FT.Refresh` to stay in sync and shares `FT.view/FT.active` with the Panel. Caches reset via `FT.liveListeners`. Test: `tests/autoguide.lua`.
- **Hub list pages:** `UI/Suggestions.lua` (Görevler page: Segmented tabs journal/available/nearby/chain, scrollable two-line rows; built by `FT.BuildSuggestions` from `CreatePanel`, replaces the old paged list in Panel) and `Map/Places.lua` (Yerler: Segmented categories, search box on the Ara tab, scroll list, save-here footer) share one pattern: Kit.Segmented + Kit.Scroll + pooled rows with `row`/`sub`/`state` fields; tests live in `tests/ingame_sim.lua`.
- **Route card (`UI/RouteCard.lua`):** when `FT.customTarget` (Yerler, Ctrl+click, search) is on another map than the player, a floating card lists `FT.RoutePlan` steps with icons from `Media/route_*.tga` (generated by `tools/make_route_icons.py`), classified via `FT.JourneyClassify`; it animates (fade-in, pulsing current step, flowing dots), closes itself on arrival in the target map, and nothing is written to chat. The world-map path in `Map/Map.lua` (`updateTrail`) draws a glow line, a dotted trail and comet lights; `FT.UpdateMapTrail(advance)` is the test hook.
- **Step details (`Guide/StepInfo.lua`):** `FT.StepInfo(step)` (verb, title, NPC, zone, detail, XP; WoWTR translation first), `FT.StepNpc`, `FT.NextStop(guide, index)`, `FT.PendingTurnIns`, and session pace `FT.Pace()` (XP/h, minutes to level). Auto-guide steps carry `npc`. The dock Rehber tab (`UI/GuideTab.lua`: NPC card, journey with icons/time/distance, "Sonra", "Yapılacaklar", pace + progress bar, Atla/Harita) and Panel's step card both use it. Pages adopted into the Hub must not capture the mouse (`EnableMouse(false)` in `adopt`), otherwise the hub cannot be dragged from the page area. The minimap draws a yellow animated route to the target (`drawRoute` in `Map/Minimap.lua`, setting `minimapRoute`). Tests: `tests/stepinfo.lua`.
- **XP forecast (`Guide/StepInfo.lua`):** `FT.TodoSummary(guide, index)` (log quests ready/active + remaining guide turn-ins: XP per row, totals, this step's share, level after ready/all) and `FT.ProjectXP(gain)` (level + fraction; thresholds above the current level are unknown, so each further level assumes ~7% more and the result is marked `~`), `FT.LevelForecast(guide, index)` ("Bu gidişle N. adımda seviye X"). The Rehber tab's "Yapılacaklar" card (`renderTodo` in `UI/GuideTab.lua`) shows it; the journey and description sections are collapsible (`gtJourneyOpen`, `gtDetailOpen` settings) and the card has a check box that completes the active step. Tests: `tests/stepinfo.lua`, Rehber block in `tests/ingame_sim.lua`.
- **Target list (`UI/TargetList.lua`):** small standalone, draggable window (`FT.targetList`, `/ftrail hedefler`, settings `targetList`, `targetListPoint`, `targetListCollapsed`) listing unfinished objectives from `FT.ActiveObjectives()`: static creature portrait (`PlayerModel` + `SetCreature`, animation frozen via `SetAnimation/FreezeAnimation/SetPaused`; falls back to an item/generic icon when the client offers none), name, counter. Click = nearest spawn via `FT.SpawnPoints` + `FT.SetCustomTarget`, right click = focus one quest, Shift+click = map, header click = collapse; progress flashes green.
- **Route ordering (`Guide/RouteOpt.lua`):** `FT.RouteOrder(steps, start, opts)` orders stops (steps) by shortest total path (nearest neighbour + move/reverse improvement) while keeping each quest's own order (accept → objective → turn-in); steps without coordinates borrow a sibling's position or go last; different continents/maps cost `FAR`. `FT.BuildRoute` (`Guide/Journal.lua`, "Rota oluştur") uses it. Test: `tests/routeopt.lua`.
- **Yol sor panel (`Map/MapRoute.lua`):** flat Kit panel beside the world map: search + "Her yer" switch, "En yakın" quick strip, category chips with per-map result counts ("Diğer" expands the rest), scrollable list (sort yakın/ad/tür, favourites = `ForeverTrailSettings.places` pinned on top, inline-expanding rows), own glow pins on the map overlay (`routeHighlight`), active-target card, collapsible. Settings: `routeCat`, `routeSort`, `routeChipsOpen`, `routeHighlight`, `routeCollapsed`, `routeSide`, `routeEverywhere`. API kept: `FT.RefreshMapRoute/RouteCategory/RouteSearch/RouteCount/MapServices`, plus `FT.RouteEntries` for tests. Tests: `tests/maproute.lua`, `tests/maproute_ui.lua` (the UI test stubs `C_Map` only after filling the service cache, and needs `ft.DBQ` set like `maproute.lua`).
- **Routes (`Map/Roads.lua`):** `FT.CurrentRoute(map, px, py, gx, gy, ww, wh)` returns a winding polyline ({{x,y},...}, first point = player) or nil (straight line). Source order: (1) the walking router `ForeverTrail_Nav` (`ForeverTrail_NavEngine` global), a load-on-demand addon loaded at the first route; (2) roads learned from the player's own walking (`ForeverTrailData.roads`, 250-cell grid per map with neighbour bit masks, A*; `roadsLearn=false` disables); (3) nil. The engine is called asynchronously with `Find(inst, {x,y}, {x,y}, cb, {waterWalking, profile})` (UnitPosition frame x=north y=west, converted with `C_Map.GetWorldPosFromMapPos/GetMapPosFromWorldPos`; never pass `walkLevel`: that selects a strict job needing Polestar's danger table); `roadsNav=false` disables; never asks in combat; re-asks on stray >60yd or a new goal; 15s back-off after a miss. Drawn by `Map/Minimap.lua` (`drawRoute`, on an upper child frame so the minimap's own render does not cover it) and `Map/Map.lua` (`trailPts`, `FT.MapRouteSegments`). `/ftrail yolbilgi` shows the active source. Tests: `tests/roads.lua`, `tests/map.lua`.
- **Cross-map targets:** a target can live on a different uiMapID than the player (city map 1454 vs Durotar 1411, neighbouring zones). `FT.ToWorld/FromWorld/ProjectToMap/ProjectStep` (Roads.lua) convert through continent world coordinates (never test map parent/child relations). Arrow falls back to a projected goal (`step.projected`, `step.world`) before `otherZone`; the minimap passes `step.world` to `FT.CurrentRoute`; the world map projects the player into the target map (may be outside 0-1: marker hidden, `clipToCanvas` keeps the first visible run of the polyline). Different continents still project to nil. The open world map switches to the target step's map once per step change (`switchedKey` in `FT.RefreshMap`). `FT.SelectNearest` stays inside a non-live guide and ignores done/skipped steps.
- **Nav addons (GPL):** `ForeverTrail_Nav`, `ForeverTrail_Nav_EK`, `ForeverTrail_Nav_Kalimdor` at the repo root are a modified copy of Polestar_Nav 0.4.2.2 (GPL-3.0-or-later; router from Shortest Path Forever by Cillian Berragan, maps are Leffe's navigation maps), renamed and with the Polestar dependency removed; see `ForeverTrail_Nav/NOTICE.md`. Never strip their copyright/licence headers (`tests/navpack.lua` checks). The game only loads top-level addon folders, so `tools/link_nav_addons.ps1` junctions them into `Interface/AddOns` (they are not in `ForeverTrail.toc`). These three folders are GPL; the rest of ForeverTrail stays MIT.
- **Autopilot (`Guide/AutoPilot.lua`):** (1) zone/login/level-up -> `FT.SuggestGuide()` asks (via `FT.ShowChoice`) whether to switch to the best recommended zone guide (`AutoGuide.Zones(map)`, climbs parent maps; silent while a hand-picked guide runs or already on that window; session decline + 2 declines = never for that window; setting `guideSuggest`). (2) `FT.AutoPilotStep()` every 2s: guide order is kept, but when the current step is >400yd away (or on another map) and a pending doable step is within 160yd the active step jumps there (15s gap; setting `autopilot`; needs `auto`). (3) `FT.Advance(auto)`: manual advance past an undone step marks it skipped (`ForeverTrailCharacter.skipped`); automatic advance (Engine.Evaluate passes `true`) does not; before completing, `FT.NextPendingStep()` returns to the first skipped-by-travel but still doable step. (4) `FT.GuideAllows(questId, kind)` / `GuideAllowsTitle`: while a non-live guide is active only its quests are auto-accepted/turned in by `Helpers/Assist.lua` (gossip, greeting, detail, progress, complete; nil = no restriction for the live journal or when `autoquestAll=true`), and the best reward is auto-picked for guide quests unless `autoreward=false`. Selecting a zone guide sets `auto` when it was never set. Tests: `tests/autopilot.lua`, Assist cases in `tests/ingame_sim.lua`.
- **Embedded quest database (`Data*.lua`, `OwnDB.lua`):** `DataQuests/Npcs/Objects/Items/Zones.lua` are large generated Questie-derived tables (MBs; coordinates stored as x10 integers; fields indexed via the `QK/NK/OK/IK` key maps in `OwnDB.lua`). `OwnDB.lua` is the query layer — don't read the Data files whole; query through it. `DataNewQuests`, `DataStations`, `DataDungeons`, `DataTalents`, and `Data.lua` (`FT.SeedData`, in-game-recorded data exported via Veri > Dışa aktar) are ForeverTrail's own additions.
- **Live data (`LiveSync.lua`):** at `PLAYER_LOGIN`, if the standalone `QuestieDB` addon (global `LibQuestieDB`, contract 4) is installed, its quest/NPC/object/item rows are converted (by field name, coords → x10 flat) and written over `FT.DBQ/DBN/DBO/DBI` in time-sliced `OnUpdate` batches. Embedded rows are the fallback; ids absent from QuestieDB (own additions) are kept. Many modules iterate those raw tables with positional indexes, so keep the embedded row layout (`QK/NK/OK/IK` in `OwnDB.lua`, column lists in `LiveSync.lua`) in sync. `/ftrail canli` shows status; `ForeverTrailSettings.noLive=true` disables. `ZoneDB`/`QuestXP` in `OwnDB.lua` ask Questie's modules (`QuestieLoader:ImportModule`, pcall-guarded) first and fall back to embedded data. Modules that cache results derived from `FT.DB*` register a reset in `FT.liveListeners`, which `LiveSync` runs when sync finishes — add one for any new cache. Tests: `tests/livesync.lua`, `tests/livezone.lua`.
- **Talent plan:** Forever has no classic talent API (trees are `C_Traits`), so `FT.TalentPlan` returns `FT.TALENT_EXTERNAL` when `FT.Compat.NumTalents(1)==0` and the UI hands off to OneForAll's Talent Trees tab via its global `OneForAll_Binding('talents')` (`FT.OpenTalentPlanner`). `/ftrail yetenekdebug` dumps the talent API state.
- **View modes:** the tracker (`Tracker.lua`) supports `c_trackerView` = detay/liste/tablo and `c_trackerMax`; the available-quests box (`Available.lua`) supports `c_availView` = kart/liste/tablo plus `c_availSort`, `c_availMax`, `availShowGiver`, `availHideLow`. `ViewOptions.lua` adds an "Ayar" button to both windows and a popup built with `FT.BuildOptions` (Settings.lua); the same keys also appear on the Settings `q_takip` page. Defaults keep the old look (detay / kart). Tests: `tests/views.lua`, `tests/viewoptions.lua`.
- **Quest info:** `QuestInfo.lua` provides `FT.QuestXPInfo/QuestXPText` (exact XP from Questie's QuestXP module or the embedded `FT.DBXP`, else a per-level median marked "tahmini") and `FT.QuestInfoTip` (the rich tooltip used by the Available box). `DataXP.lua` is generated from QuestieDB's `xpDB-traces.lua` and overrides `FT.DBXP` (it is what covers Forever-only quests). Test: `tests/questinfo.lua`.
- **Quest window (`UI/QuestDock.lua`):** the tracker (`FT.tracker`) and available-quests box (`FT.availableBox`) live inside one tabbed window (`FT.questDock`). The two boxes keep their own logic; the dock re-parents them and redirects their `Show/Hide/IsShown/SetScale` to it ("wanted visibility"), so other modules can keep calling them. Use `FT.QuestFrame()` for positioning, never the boxes directly. `FT.BuildQuestDock()` builds it; on failure the old two-box layout stays.
- **Guide tab scrolling and the game's own tracker (`UI/QuestDock.lua`):** the Rehber content (`FT.guideBox`) lives inside a `Kit.Scroll` (`FT.guideScroll`) so it is clipped to the window and scrolls with the mouse wheel when the window is resized small (it used to spill below the window over the world); visible height = `dockH - tab strip` when the height is set by hand, else content height capped at 88% of the screen (`dock.guideView/totalH` are the test hooks); `Kit.Scroll` has `sf:SetBarInset(v)` (scroll bar sits `v` px outside the right edge; negative keeps it inside a full-width area). `FT.ApplyBlizzTracker` hides/shows whichever of `ObjectiveTrackerFrame`/`QuestWatchFrame`/`WatchFrame` exists according to setting `blizzTracker` (default OFF = hidden, so only the ForeverTrail quest window shows; an `OnShow` hook re-hides it when the game re-shows it; never touches it in combat, re-applies on `PLAYER_REGEN_ENABLED`). Settings: Görev kutuları page. Tests: 'Rehber sekmesi küçülünce kırpılır ve kaydırılır', 'oyunun kendi takipçisi ayarlardan açılıp kapanır' in `tests/ingame_sim.lua`.
- **Quest list (`UI/QuestList.lua`):** while the quest window exists, `FT.RefreshTracker` is redirected to `FT.RefreshQuestList` (new renderer: summary, zone headers, one contiguous clickable block per quest, scrollable). The old row drawing in `Tracker.lua` only runs when the window is absent. It reuses the same saved keys (`trkPin`, `trkMin`, `trkZones`, `trkOrder`, `c_tracker*`) and helpers (`FT.ObjectiveProgress`, `FT.TrackerItemButton`, `FT.QuestRowTip`).
- **Step-by-step quest text (`FT.QuestSteps` in `Guide/StepInfo.lua`, drawn by `drawSteps` in `UI/QuestList.lua`):** under each logged quest the list shows numbered steps: one per objective ("Öldür/Topla/Kullan: <name>", counter, place line "Bölge · 45, 62" from the nearest spawn via `FT.PlaceOf`) and always a last "Teslim et: <NPC>" step with its place. Done steps are green and hidden when `trkHideDoneObj`; the first undone step is highlighted and gets the progress bar. Counters are read from the quest log on every call; only places are cached (5s, reset by `FT.liveListeners`). `FT.ActiveObjectives` rows now carry `name`. Setting `trkSteps` (default on; Settings "kutu" tab, view-options popup); minimized quests and the compact view stay one-liners. Tests: QuestSteps block in `tests/stepinfo.lua`, "numaralı adımlar" block in `tests/ingame_sim.lua` (`FT.QuestListStepRows` hook).
- **Quest detail tooltip (`FT.QuestDetailTip` in `UI/QuestInfo.lua`):** one opaque Kit tooltip with everything about a quest: status line, objective text and story (WoWTR first), a media strip (`tip:AddMedia{npc, icons}`: frozen 3D portrait of the objective/turn-in/giver creature via `PlayerModel`, objective + reward item tiles with quality borders), the numbered plan, reward/XP, level, chain, distance. `FT.QuestInfoTip` (Available box, lists) and `FT.QuestRowTip` (quest list rows) delegate to it; it falls back to plain lines on a bare GameTooltip. WoW quests carry no images, so portrait + item icons are the "picture". `FT.QuestPlan(questId)` = `FT.QuestSteps` when logged, else a DB preview ("Görevi al: NPC" + objectives + turn-in; empty when turned in). `Kit.Tooltip` must hide pooled parts beyond the ones used (stale parts used to ghost over the next tooltip). Placement (`Kit.PlaceTip`, pure and tested): the tooltip opens OUTSIDE the owner's top-level window (first ancestor under UIParent): beside it for `ANCHOR_LEFT/RIGHT` (preferred side if it fits, else the other, else the roomier one) or above/below for `ANCHOR_TOP/BOTTOM`, clamped to the screen; it falls back to the old anchors when frame rects are unavailable. The tooltip frame is always opaque (solid base + halo under the panel fill).
- **Guide tab plan (`UI/GuideTab.lua`):** under the step card a collapsible "Bu görevde" section lists `FT.QuestPlan(step.questId)` (settings `gtPlan` on/off, `gtPlanOpen` collapsed); the card's and the Yapılacaklar rows' tooltips use the detail tooltip. Hook: `FT.GuideTabPlanRows`. Tests: 'rehber: bu görevde adımlar ve ayrıntılı ipucu' and 'ipucu hayalet satır' in `tests/ingame_sim.lua`, QuestPlan block in `tests/stepinfo.lua`.
- **Quest requirements (`Guide/Requirements.lua`):** `FT.QuestRequirements(questId)` lists what is still missing before a quest can be done, from the character's REAL state (`C_QuestLog.IsQuestFlaggedCompleted`, `FT.turnedIn`, log, `GetItemCount`), cached 3s: unmet prerequisite quests (`preQuestGroup` = all, `preQuestSingle` = any one; skipped once the quest is logged) and objective items that have no drop source but come from another unfinished quest (reward or `sourceItemId` given on accept) and are not in the bags. Entries: `{kind='quest'|'item', text, detail, where, place, npc, questId, ...}`; `FT.QuestSpot(id, 'accept'|'turnin')` (StepInfo) gives the giver's place (NPC via `FT.SpawnPoints`, which only knows NPCs, then startedBy/finishedBy OBJECTS (bulletin boards, books), then, for item-started quests, the spots where the item drops; `FT.QuestGiverName`, `FT.QuestStartItem`, `FT.QuestZoneName` give the name / starting item / zone when no exact spot exists, so a requirement says "Eşyayla başlar: X" or "Durotar (tam konum verisi yok)" instead of nothing; on real data ~97% of prerequisite quests get an exact spot), `FT.GoToRequirement(req)` routes there via `FT.SetCustomTarget`. Entries can be `ready` (a prerequisite quest started by an ITEM whose item is already in the bags: "sağ tıkla, görevi başlat"; or a logged prerequisite whose objectives are done: only the turn-in is left): they stay visible but green in the Guide tab/tooltip, and `FT.UnmetRequirements(id)` (used by the list badges, the popup and the quest rows) leaves them out. Watched items (start items and objective items) are remembered with their bag counts; `FT.RequirementsBagChanged` (driven by debounced `BAG_UPDATE_DELAYED`/`BAG_UPDATE`, and only when a watched count actually changed) clears the cache and refreshes `FT.Refresh/RefreshTracker/RefreshAvailableBox`, so the warning disappears when the item is picked up and returns if it is lost. An item-started prerequisite also says where its item comes from (`dropInfo`: dropping NPCs and, via `NK` zoneID in `FT.DBDungeons`, the dungeon, e.g. "düşer: Edwin VanCleef (The Deadmines zindanı)"); for such quests the quest-zone fallback is NOT shown as a place (it is the turn-in zone, not where the item is). Bag checks use `GetItemCount(id)` and, when that is 0, a by-NAME scan of the bags (`bagHasName`), because the item id in the database can differ from the one in the game. `/ftrail gereksinim [quest id]` (`FT.RequirementsDebug`) prints why a quest has requirements (prerequisites, objective items with bag count by id/by name, drop sources, giver quests); use it first when a warning looks wrong. Facts about the live `QuestieDB` addon (data baked as base64 CBOR in `QuestieDB_Forever.toc`; field numbers differ from our embedded `QK/IK` layout, which `LiveSync` maps by field NAME): its quest rows also carry `requiredSourceItems` (field 21, 118 quests) and `parentQuest/childQuests`, which ForeverTrail does not read yet. Shown in the Guide tab (amber block above "Bu görevde", click = route), `FT.QuestDetailTip` ("Dikkat:" lines), the Görevler list ("Önce gerekli" state) and Available box (amber `!`); `FT.StepRequirementWarning` (called from the Guide tab's `FT.Refresh` wrapper) opens a `FT.ShowChoice` popup once per quest per session (setting `reqWarn`); `doable()` in `AutoPilot.lua` skips objective steps whose item is missing. The zone-guide builder (`AutoGuide.lua`) is cached per race/class and does not know character progress, which is why this check runs at use time, not build time. Tests: `tests/requirements.lua`, 'rehber: eksik ön koşul ve eşya uyarısı' in `tests/ingame_sim.lua`, objective case in `tests/autopilot.lua`.
- **Window dragging (`Kit.DragThrough` / `Kit.DragThroughTree` in `Core/Kit.lua`, `FT.HubDragScan` in `UI/Hub.lua`):** in WoW the frame under the cursor gets the mouse-down and a drag never bubbles to the parent, so any mouse-capturing child (a ScrollFrame, which captures because of `EnableMouseWheel`; big rows/buttons; mouse-enabled containers) makes the window undraggable over its area, and per-page `EnableMouse(false)` patches never covered new lists. `Kit.DragThrough(f)` makes a frame forward `OnDragStart/OnDragStop` to its nearest movable ancestor that has its own `OnDragStart` (the window keeps its own move/save logic, e.g. the Hub saves `hubPoint`). `Kit.Scroll` applies it at creation, so every Kit list is covered; `Kit.DragThroughTree(root)` covers raw ScrollFrames and mouse-capturing Buttons/Frames of at least 80x18 (only ScrollFrame/Button/Frame kinds, so Slider/EditBox/CheckButton are never touched; skips frames that already have `OnDragStart/OnMouseDown/OnMouseUp` such as resize grips, and small icons/close buttons). The Hub scans on open and every 1.5s while shown (pooled rows are created lazily). The quest window (`UI/QuestDock.lua`, tabs Rehber/Görevlerim/Alınabilir) forwards from its tab buttons and the adopted tracker/available boxes explicitly and rescans every 1.5s. The layout lock (`ForeverTrailSettings.locked`, `/ftrail kilit`, `FT.ToggleLock`) used to freeze the quest window, available box, tracker, arrow and strip with no sign at all, which looked like "the window cannot be moved" (the real cause of a long-running bug report). Now: every `OnDragStart` goes through `FT.CanDrag()` (Shift+drag moves even when locked; otherwise `FT.LockedHint()` says why, at most once per 15s); the quest window's tab strip has an always-visible lock button left of "Ayar" (filled accent when locked, dim when open, click toggles; `FT.RefreshQuestDockLock`); `FT.MigrateLayoutLock` (called from `Engine.Initialize`, `lockVersion`) clears a forgotten lock once; saved profiles (`Guide/Flow.lua`) never store or restore `locked/arrowLocked`. Tab padding shrinks with the window width (`FT.QuestDockTabPad`) so the tabs no longer run under the right-hand buttons. The Hub ignores the lock. New window code: never add a mouse-capturing frame without forwarding its drag. Test: 'hub: sürükleme her yerden pencereyi taşır' in `tests/ingame_sim.lua` (the sim now models `SetMovable/IsMovable`).
- **Icon strip (`UI/Features.lua`, `FT.CreateDock`, `/ftrail cubuk`):** flat Kit bar (`rail` fill, `line` edge) of `dockButton`s: mono glyphs `Media/dock_*.tga` (generated by `tools/make_dock_icons.py`) tinted from the theme (muted, text on hover, accent + 2px underline while "on": Panel = hub open, Sessiz = `FT.IsSilent`, Kilit = `locked`), Kit tooltip, a divider before Araçlar/Kilit, and a small rotate button at the end (setting `dockVertical`: the strip lays out horizontally or vertically via `FT.DockMetrics`/`layoutDock`; tooltips open above/below a horizontal strip and beside a vertical one). `FT.RefreshDock` calls each button's `Refresh`. To add a button: add a row to `primary` (name, tip title, tip text, glyph, handler, optional isOn) and a glyph in the generator. Test: 'ikon şeridi' block in `tests/ingame_sim.lua`.
- **Quest-item guard:** `QuestItems.lua` — `FT.IsProtectedItem(itemID, classID)` (quest class, objective/source items of logged quests via QuestieDB, or `ForeverTrailSettings.lockedItems`) is checked by `isJunk` in `Gear.lua`; on `MERCHANT_UPDATE` it also buys protected items back from the vendor buyback list. `FT.ToggleQuestItems` / `/ftrail gorevesya` is the bag-item window. Setting `questItemGuard` (default on). Test: `tests/questitems.lua`.
- **UI layers** (Panel, Tracker, Map/MapRoute/Arrow/Minimap, Hub, Settings, Journal/Journey, Atlas, Layout/Design/Style/Polish, Wizard, etc.) are independent feature modules hanging off `FT`; settings live in `ForeverTrailSettings` (account), `ForeverTrailCharacter` (per-char guide/step), `ForeverTrailData`, `ForeverTrailBackup`.
- **Companion-addon integration:** `QuestieMerge.lua` detects an embedded/loaded Questie and exposes `FT.QuestieOverlaps` / `FT.QuestonOverlaps` — lists of ForeverTrail features (tracker, ! / ? icons, auto-quest, plate icons, …) that get disabled when Questie or Queston provides the same thing, to avoid duplicates. `QuestieBridge.lua`, `QuestonBridge.lua`, `QuestieUI.lua`, `QuestonTR1/2.lua` add ForeverTrail's settings into those addons' option windows and load Turkish locale via their public APIs without modifying their files. Optional WoWTR dependency supplies Turkish quest titles/objectives.
- **Vendored third-party trees:** `Questie/` and `QuestieDB/` (GPL-3.0, with their own licenses/Libs) are bundled upstream code. Treat them as vendored: don't refactor them; ForeverTrail's own code is the top-level `*.lua` files (MIT, see `LICENSE`). Neither tree is listed in `ForeverTrail.toc`.

## Conventions

- Third-party code/data must not be copied into ForeverTrail's own files except the already-bundled GPL Questie data and the GPL `ForeverTrail_Nav*` copy (kept in its own folders with notices); the README documents that Zygor etc. were only consulted for workflow, not copied.
- Protected-API safety: `C_Map` and other client calls are wrapped in `pcall` and nil-checked because they are not live-verified on this client; keep that pattern. Never modify or delete another addon's map pins/waypoints.
- Location-step checks are throttled (~1s); don't scan the quest log per frame.
